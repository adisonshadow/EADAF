# 应用导出/导入 方案计划

> 状态：**待审阅**（本文档仅为设计方案，未做任何实现）
> 日期：2026-09-07
> 入口：系统设置 `/system/settings` 新增 Tab「导出/导入应用」

---

## 1. 背景与目标

为便于将某个应用及其依赖的完整数据从一个 EADAF 实例迁移/复制到另一个实例，提供按应用维度的**业务数据 JSON 导出/导入**能力（区别于现有 `.dump` 整库备份/恢复）。

- 导出：选择一个应用，按规则收集该应用依赖的全部设计与数据，生成单个 `.json` 文件下载。
- 导入：上传导出文件，预览摘要与冲突，选择冲突策略后分节导入。

**明确不做**（本方案范围外）：整库备份（已有）、菜单/路由迁移、存储桶文件内容迁移（可作为后续扩展）。

## 4. 导出范围与筛选规则（核心）

统一记号：设所选应用为 A。

- **A 的顶层 Scope 集合** `T(A)` = `A.bizdata_scope_codes` 各项按 `:` 切分后的首段去重集合（如 `["IPS","CRM:bom"]` → `{"IPS","CRM"}`）。
- **前缀命中**：`code === s || code.startsWith(s + ':')`，与现有 `matchesApiDataScope` 等逻辑一致。

| # | 内容 | 筛选规则 | 附带 | 排除 |
|---|---|---|---|---|
| 1 | 应用本体（**始终导出**） | `uac.applications` 中 A 的整行（含 `api_enabled`、`api_connect_config`、`api_data_scope`、`builtin_api_scope`、`outbound_webhook_scope`、`bizdata_scope_codes`、`top_level_skill_markdown`、`sso_*`、logo 等） | — | `created_at/updated_at/deleted_at` 之类审计列不导出，导入时重新生成 |
| 2 | 数据实体设计（**结构始终导出**） | `bizdata.entities` 中 code 前缀命中 `A.bizdata_scope_codes` 任一项的实体（全部状态） | 全部 `bizdata.entity_fields`；相关 `bizdata.scope_docs`；行数据涉及到的 `bizdata.database_connections` | — |
| 3 | 实体行数据（受「导出内容」控制） | 上述实体的物化表数据。`数据和结构`=结构+数据；`仅数据`=只导数据但记录导出时 `entity.version`。`json_schema` 类实体无物理表、无行数据 | 每个数据集记录 `entityCode / entityVersion / connectionId / tableName / columns / rows` | — |
| 4 | 应用 API 服务 | 优先按 `A.api_data_scope`：`serviceCodes` 精确 + `domainCodes` 前缀命中 `bizdata.api_services`；`api_data_scope` 为空则回退 `bizdata_scope_codes` 前缀命中 | 每服务的 `api_service_operations`、`api_service_permissions`（含 grant_type='application' 指向 A 及其他授权行，导入时重映射） | `api_service_runs` 运行记录 |
| 5 | 采集管道（采集数据结构化） | `bizdata.collection_pipelines` 中 **code 首段 ∈ T(A)** 的管道 | `collection_pipeline_applications` 来源白名单行 | `collection_pipeline_runs` |
| 6 | 提交外部API | `bizdata.outbound_webhooks` 中 **绑定的业务 API**（`trigger_api_service_code`）**首段 ∈ T(A)** 的 webhook | — | `outbound_webhook_runs` |
| 7 | SKILL / Tools | `aibase.skills`：`is_global=true` 的全部 + `is_dedicated=true` 且经 `skill_applications` 绑定 A 的 | 对应 `skill_tools`、`aibase.tools`、skill/tool 引用的 `aibase.scopes` 行、A 相关的 `skill_applications` 行 | — |
| 8 | AI 数据（勾选才导出） | `aibase.providers`、`aibase.models`、`aibase.model_capabilities`、`aibase.model_io_tags` **全量** | — | `api_request_logs` |
| 9 | 用户/组织/权限（勾选才导出**数据**） | 全量：`users`、`departments`、`department_closure`、`roles`、`permissions`、`user_roles`、`role_permissions`、`department_roles`、`data_permission_rules`、`builtin_api_configs` | — | 登录辅助表（refresh_token/captcha/login_attempt/password_reset）、`operation_log` |
| 10 | EADAF 最小结构（**未勾选 9 时也导出**） | 「无论如何，结构是一定导出的」：被本次导出内容**引用**的 `permissions`（`A.builtin_api_scope.permissionCodes`、导出的 `api_service_permissions` 等引用的 code）与对应 `roles` 定义 | — | 用户/组织/个人授权数据 |

> 说明：第 10 条是对需求原文「是否包含 用户/组织/权限 数据 确认后，导出数据包含相关数据，注意，无论如何，结构是一定导出的」的实现解读——勾选=结构+全部数据；不勾选=仅导出保证导入后引用完整性所需的最小权限/角色结构。**此解读见待确认问题 2。**

## 5. 导出文件格式

单文件 JSON（UTF-8），文件名 `eadaf-app-export-{appCode}-{yyyyMMddHHmmss}.json`。

```jsonc
{
  "format": "eadaf-app-export",
  "formatVersion": 1,
  "exportedAt": "2026-09-07T10:00:00.000Z",
  "source": { "applicationId": "uuid", "appCode": "CRM", "appName": "客户管理" },
  "options": { "dataMode": "structure_and_data", "includeUac": false, "includeAi": true },

  "application": { /* uac.applications 行（去掉审计列） */ },

  "entities": {
    "items":    [ /* bizdata.entities */ ],
    "fields":   [ /* bizdata.entity_fields（entityId 为导出源 id，导入时重映射） */ ],
    "scopeDocs":[ /* bizdata.scope_docs */ ],
    "connections": [ /* 行数据引用的 bizdata.database_connections */ ]
  },
  "entityData": [
    {
      "entityCode": "CRM:customer",
      "entityVersion": 3,
      "entityKind": "er_table",
      "connectionId": "uuid",
      "tableName": "crm_customer",
      "columns": ["id", "name", "..."],
      "rows": [ { "...": "..." } ]
    }
  ],

  "apiServices": {
    "items":       [ /* bizdata.api_services */ ],
    "operations":  [ /* api_service_operations（serviceId 源 id） */ ],
    "permissions": [ /* api_service_permissions（grant_id 源 id） */ ]
  },

  "collectionPipelines": {
    "items":       [ /* collection_pipelines */ ],
    "applications":[ /* collection_pipeline_applications */ ]
  },

  "outboundWebhooks": { "items": [ /* outbound_webhooks */ ] },

  "skills": {
    "items":            [ /* aibase.skills */ ],
    "skillApplications":[ /* skill_applications */ ],
    "skillTools":       [ /* skill_tools */ ],
    "tools":            [ /* aibase.tools */ ],
    "aiScopes":         [ /* aibase.scopes */ ]
  },

  "ai": {
    "providers":    [ /* aibase.providers */ ],
    "models":       [ /* aibase.models */ ],
    "capabilities": [ /* aibase.model_capabilities */ ],
    "ioTags":       [ /* aibase.model_io_tags */ ]
  },

  "uac": {
    "users": [], "departments": [], "departmentClosure": [],
    "roles": [], "permissions": [],
    "userRoles": [], "rolePermissions": [], "departmentRoles": [],
    "dataPermissionRules": [], "builtinApiConfigs": []
    /* 未勾选时仅填 roles / permissions / dataPermissionRules 的最小引用集 */
  }
}
```

## 6. 后端接口设计

新增路由文件 `backend/src/routes/appTransferRoutes.js`，`prefix: '/api/v1/system/app-transfer'`，挂载到 `routes/index.js`；中间件沿用 `authWithBuiltinApiGuard` + `operationAudit`（import 写操作必挂，export 只读可只挂守卫）。

| 接口 | 方法/入参 | 返回 |
|---|---|---|
| 导出 | `POST /export`，JSON body：`{ applicationId, dataMode: 'structure_and_data' \| 'data_only', includeUac, includeAi }` | `{ code, data: { fileName, payload: <第5节对象> } }`；前端负责落盘下载 |
| 导入预览（可选） | `POST /preview`，multipart `file` | 分节条数、按唯一键检测到的冲突清单（目标已存在记录）、缺失引用警告 |
| 导入执行 | `POST /import`，multipart `file` + `strategy`（`overwrite` \| `skip` \| `abort`），koa-body 上传同备份恢复模式（临时目录，限 `.json`，上限如 1GB） | 分节结果：每节 `{ created, updated, skipped, failed, errors[] }` 及总览 |

控制器 `controllers/appTransferController.js`；服务 `services/appTransfer/appExportService.js`、`appImportService.js`。

若内置 API 守卫需要权限登记，则按 `services/builtinApi/catalog.js` 现有格式补 `system:appTransfer:export` / `system:appTransfer:import` 权限码（实现时以 `withBuiltinApiGuard` 对 systemRoutes 现有接口的实际要求为准，照抄配置方式）。

导出数据量可能较大：导出接口使用长超时；后端逐节 `findAll`（行数据用连接直连 `SELECT *`，经 `raw` 查询），单节点内存可接受（内网系统）；预留 `maxRowsPerEntity` 参数不做默认限制，文档中注明性能风险。

## 7. 导入设计与冲突处理

### 7.1 唯一键与 upsert

| 表 | 唯一键 |
|---|---|
| `uac.applications` | `code` |
| `bizdata.entities` | `code` |
| `bizdata.api_services` / `collection_pipelines` / `outbound_webhooks` | `code` |
| `aibase.scopes` / `tools` / `skills` / `providers` / `models` | `slug` |
| `uac.roles` | `code`；`uac.permissions` | `code` |
| `uac.users` | `username` |
| `uac.departments` | **无唯一键**：按 `(name + 父链路径)` 匹配，匹配不到则新建 |
| `bizdata.database_connections` | 按 `name` 匹配；匹配不到回退目标实例默认 PG 连接（`bizdata.settings.default_materialization_schema` 对应种子连接） |
| `uac.builtin_api_configs` | `code` |

### 7.2 ID 重映射

导入时**所有 UUID 重新生成**，内存维护 `idMap: { tableName: { oldId: newId } }`，对全部外键重映射：`entity_fields.entity_id`、`api_services.entity_id/connection_id`、`api_service_permissions.grant_id`（application/role/department 分别查对应映射）、`trigger_api_service_id`、`collection_pipeline_applications.*`、`skill_applications.*`、`skill_tools.*`、`tools.scope_id`、`skills.scope_id`、`models.provider_id`、EADAF 各关联表。`department_closure` 导入后按新部门树重建。

### 7.3 冲突策略

- `overwrite`（默认）：按唯一键覆盖更新目标记录（含子表整体替换，如 entity_fields、api_service_operations）。
- `skip`：目标已存在则跳过该记录及其子表。
- `abort`：预检发现任何冲突即终止，返回冲突清单。

### 7.4 导入顺序（分节执行，失败节不影响其他节，结果分节报告）

1. `uac`（先结构后数据；含 builtin_api_configs）
2. `entities` 结构（items + fields + scope_docs；实体按 `overwrite` 更新时 version 取文件中版本）
3. 物化：对 `er_table` 实体调用现有 `materializationService.executeMaterialization`（带 `expectedVersions` 乐观锁）
4. `entityData` 行数据：经 `database_connections` 直连目标表批量插入。**版本校验**：`entityData.entityVersion ≠ 目标实体当前 version` 时按策略跳过并在结果中告警（防止数据写错结构的表）
5. `apiServices`（items → operations → permissions）
6. `collectionPipelines`
7. `outboundWebhooks`
8. `skills`（aiScopes → tools → skills → skillTools → skillApplications）
9. `ai`（providers → models → capabilities → ioTags）

主库各节尽量包在 Sequelize 事务中；行数据写入目标外部库，无法与主库同事务，靠分节报告兜底。

### 7.5 行数据连接类型支持

行数据导出/导入 v1 仅支持 SQL 类物化连接（**PostgreSQL / MySQL**，与 `materializedTableBrowseService` 的连接方式一致）；MongoDB / Redis 连接的实体**跳过行数据**并在导出/导入结果中提示。见待确认问题 4。

## 10. 边界情况与风险

1. **两套 Scope 体系**：数据域（冒号 code 虚拟树）与 AI 域（`aibase.scopes` 表）互不相关；Skill/Tool 导出时必须连同 `aibase.scopes` 行一起按 `slug` upsert。
2. **软删（paranoid）**：`applications`、`users` 等带软删的表，导出仅取未删除记录。
3. **实体「仅数据」导入的结构依赖**：目标实体不存在或版本不一致时按策略跳过并明确报告，不静默失败。
4. **JSON 导入体积**：koa-bodyParser 默认限制不适用于 multipart 上传路径（走 koa-body 临时文件），与备份恢复同模式。
5. **导入的幂等性**：重复导入同一文件，在 `overwrite` 策略下结果一致（按唯一键 upsert）；`skip` 策略下二次导入全部跳过。
6. **内置应用 EADAF**：系统应用，承担内置 API 目录聚合职责，建议禁止导出（见待确认问题 5）。
7. **性能**：行数据全量导出/导入在大表（>10 万行）时耗时较长；v1 接受，界面给出长任务 loading 与结果耗时，后续可加 maxRows/分批。
