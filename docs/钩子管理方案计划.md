# 钩子管理（Hook Center）功能方案计划

> 状态：**待审阅**（本文档为方案计划，尚未实施）
> 日期：2026-08-31
> 产品入口：**API 服务 → 钩子管理**（`/api_services/hooks`）
> 关联文档：[outbound-webhook-evolution.md](./outbound-webhook-evolution.md)（P3 路线即本方案）、[external-app-integration-guide.md](./external-app-integration-guide.md)（入站方向，互补）

---

## 1. 背景与目标

EADAF 目前唯一的"钩子"能力是「提交外部 API」（Outbound Webhook）：仅在业务 Data API HTTP 调用成功后触发一次 HTTP 外呼。`outbound-webhook-evolution.md` 早已给出判断：**出现第二类触发源、需要跨模块统一订阅与多种动作类型时，应抽取独立钩子/事件中心（P3）**。

本方案正是那个时机的落地：

- **多触发源**：用户登录/登出、实体记录创建/更新/删除、API 服务被调用、定时（cron）
- **多动作类型**：调用外部 HTTP、调用内部 API 服务、执行一段 TypeScript 脚本
- **AI 辅助**：用户用自然语言描述（如"订单金额超过 1 万就通知我"），AI 帮忙创建、编辑、测试钩子

### 目标用户

管理员/业务搭建者（**非专业程序员**）。因此产品原则是：

1. 表单化配置为主，脚本为进阶选项；
2. 一切能力和数据（事件负载、运行结果）都要"看得见"；
3. 出错不神秘——失败有记录、可重试、可回放。

### 非目标（第一期明确不做）

- ❌ 同步拦截/否决主操作（如"更新前校验、不通过则拒绝"）——已确认仅**事后异步**，未来需要时再设计"同步校验钩子"类型
- ❌ 脚本内网络访问（fetch）——HTTP 需求用「调用 API」动作类型实现，后续版本再考虑受信主机 `ctx.http`
- ❌ 持久化消息队列（引入 bullmq 等）——第一期用进程内异步执行，代价与边界见 §18 风险
- ❌ 可视化工作流编排（多步骤 DAG）——单钩子 = 单事件 + 单动作，链式场景用"钩子调 API → API 再触发事件"自然组合（有递归深度保护，见 §8.4）

## 2. 已确认的产品决策

| 决策点 | 结论 | 备注 |
|---|---|---|
| 执行语义 | **仅事后异步** | 钩子在事件完成后触发，不阻断、不修改主流程；登录/API 响应耗时不受影响 |
| 与现有「提交外部 API」关系 | **统一收编** | HTTP 外呼成为新钩子的一种动作类型；旧 webhook 数据迁移、旧入口逐步下线 |
| 第一期触发源 | 登录、登出、记录创建/更新/删除、API 服务被调用、定时 cron | 另有手动测试触发（不计入正式运行） |
| 菜单入口 | 挂在「API 服务」分组下 | `/api_services/hooks`，与「提交外部 API」「采集管道」并列 |

## 3. 容易遗漏的能力清单（补充建议）

原始需求只提到"事件触发 + API/TS 脚本动作 + AI 辅助"。以下是完整落地必须、但容易忽略的能力，**每项都已纳入本方案**：

| # | 能力 | 为什么需要 | 本方案的取舍 |
|---|---|---|---|
| 1 | **条件过滤** | 不过滤的话，任何一个事件都会触发所有钩子（每次登录都跑一遍全部钩子） | 三级过滤：实体/操作类型 → 字段变更（changed_fields）→ 可选 JS 布尔表达式 |
| 2 | **防循环触发** | 钩子 A 更新了记录 → 触发记录更新事件 → 又执行钩子 A → 死循环 | 事件负载携带 `depth`，≥3 拒绝执行并记 skipped、醒目告警 |
| 3 | **重试与失败处理** | 网络抖动、外部系统偶尔 500 是常态，一次失败就丢不可接受 | 默认自动重试 2 次（指数退避）；连续失败 N 次（默认 10）自动禁用并标记，等人工处理 |
| 4 | **超时与资源限制** | 脚本死循环、外部接口挂起会拖垮进程 | 脚本默认 5s 超时（复用现有 vm 沙箱）；HTTP 15–60s；单钩子并发上限 |
| 5 | **运行历史（Run）** | "钩子到底跑没跑？结果是什么？"必须可查 | 每次执行记录：输入 payload、输出、耗时、错误、重试次数；保留 30 天自动清理 |
| 6 | **重放（Replay）** | 修好钩子后想把失败的那次重跑一遍 | 用历史 run 的原 payload 一键重试 |
| 7 | **测试能力** | 不能等真实事件发生才知道钩子对不对 | mock 负载 dry-run + 引用历史真实 payload 试跑；测试不产生新的运行记录污染统计 |
| 8 | **真正异步（非阻塞）** | 现有 outbound webhook 是 `await` 在业务 API 请求路径上的（性能隐患，其 P2 待办） | 新钩子中心 fire-and-forget；收编时顺带修复此问题 |
| 9 | **性能（注册表缓存）** | 每次 API 调用/记录写入都要查一遍"有哪些钩子"，不能每次都打 DB | 钩子注册表内存缓存：启动加载、CRUD 变更时失效重建（复用 metricScheduler 的 DB 配置驱动模式） |
| 10 | **密钥管理** | 外呼鉴权密钥不能明文存、不能回显 | 复用 webhook 现成实现：加密落库、编辑页掩码、空提交保留旧值 |
| 11 | **变更前后数据（before/after）** | "金额从多少改成多少"是钩子最常用的信息；目前执行服务不返回 before | 小改 `apiServiceExecutionService` 写操作返回 `{before, after}`（见 §5.2） |
| 12 | **事件负载文档化** | 用户和 AI 都需要知道"每个事件会给我什么数据" | 事件目录 API（`GET /event-types`）：事件类型 + 负载 JSON Schema + 示例，前端表单和 AI 提示词共用同一份 |
| 13 | **权限与审计** | 钩子能外呼、能查库，不能人人可建 | 菜单权限码 `api_services:manage`（随分组既有权限）；`created_by` 审计；运行历史全量留痕 |
| 14 | **草稿状态** | 没配完的钩子不能生效 | 状态机：`draft → enabled ⇄ disabled`（+ 连续失败自动 `auto_disabled`） |
| 15 | **运行统计** | 管理员需要一眼看出"哪个钩子总在失败" | 列表页展示最近成功率/最近运行状态，失败率高醒目标红 |

## 4. 核心概念与整体架构

### 4.1 概念模型

```
┌─────────┐     emit()      ┌──────────────┐    匹配过滤     ┌──────────┐
│ 事 件   │ ──────────────▶ │  事件分发器   │ ──────────────▶ │ 钩子(多条)│
│ Event   │   (异步,不阻塞)  │ EventDispatcher│  (内存缓存)    │  Hook    │
└─────────┘                 └──────────────┘                 └────┬─────┘
                                                                 │ 执行动作
                                                    ┌────────────┼────────────┐
                                                    ▼            ▼            ▼
                                              调用外部 HTTP   调用内部 API   TS 脚本
                                                    └────────────┼────────────┘
                                                                 ▼
                                                        ┌────────────────┐
                                                        │ 运行记录 Run    │
                                                        │ (成功/失败/重试) │
                                                        └────────────────┘
```

| 概念 | 说明 |
|---|---|
| **事件 Event** | 系统中发生的一件事。类型如 `auth.user.login`、`bizdata.record.updated`；每次发生携带一份负载（payload） |
| **钩子 Hook** | 一条规则：**当**某事件发生（且满足过滤条件）**则**执行某动作。含名称、状态、失败策略 |
| **动作 Action** | 钩子触发后做的事：`http_request`（外呼）/ `internal_api`（调内部已发布 API 服务）/ `script`（TS 脚本） |
| **运行 Run** | 钩子的一次执行记录：输入、输出、状态、耗时、错误、重试次数 |

### 4.2 一条钩子的完整生命周期

1. 管理员（手工或 AI 辅助）创建钩子 → 状态 `draft`
2. 在测试面板用 mock/历史负载试跑 → 通过后 `enabled`
3. 事件发生 → 分发器匹配 → 异步执行 → 写 Run
4. 失败 → 自动重试（退避）→ 仍失败计入连续失败计数
5. 连续失败达阈值 → 自动 `auto_disabled` + 列表醒目标记 → 人工修复后重新启用
6. 运行记录按保留策略自动清理（默认 30 天）

## 5. 事件源设计（第一期）

### 5.1 事件目录

| 事件类型 | 触发时机 | 负载要点 |
|---|---|---|
| `auth.user.login` | 登录成功后 | `user_id`、`username`、`ip`、`user_agent`、`login_at` |
| `auth.user.logout` | 登出成功后 | `user_id`、`username`、`logout_at` |
| `bizdata.record.created` | Data API 写入成功后 | `entity_code`、`record`（创建后全文）、`api_service_id` |
| `bizdata.record.updated` | Data API 更新成功后 | `entity_code`、`before`、`after`、`changed_fields[]`、`api_service_id` |
| `bizdata.record.deleted` | Data API 删除成功后 | `entity_code`、`before`（被删记录全文）、`api_service_id` |
| `apiservice.invoked` | Data API 调用完成后（成功与失败都发） | `api_service_id`、`operation`、`status`(success/failed)、`duration_ms`、请求摘要、响应摘要 |
| `schedule.cron` | cron 到点 | `cron` 表达式、`fire_at`；过滤条件用 cron 本身区分不同定时钩子 |
| `manual.test` | 测试面板/AI 试跑 | 仅测试路径，payload 由用户选择或 mock |

每个事件的完整 JSON Schema + 示例由 `GET /api/v1/automation/hooks/event-types` 下发（单一事实源，前端表单、AI 提示词、本文档共同引用）。

### 5.2 触发点接线（基于现有代码）

| 事件 | 接线位置 | 说明 |
|---|---|---|
| 登录/登出 | `backend/src/controllers/authController.js` 登录成功路径（约 203 行后）、logout 成功后 | 目前登录后无任何钩子逻辑，纯新增一行 `emit()` |
| API 调用 + 记录增删改 | `backend/src/services/apiService/apiServiceInvokeService.js` 的 `invokePublished`（约 92–101 行，现有 `triggerByApiService` 调用处） | **替换**为统一 `emit()`：先发 `apiservice.invoked`，再按 operation 类型发 `bizdata.record.*` |
| before/after | `apiServiceExecutionService.js` 写操作（`executeCreatePg` / `executeUpdateOnePg` / `executeDeleteOnePg`，约 283–323 行） | 小改：update 先读 before 再更新并返回 `{before, after}`；create/delete 返回对应数据；上层透传给事件负载 |
| cron | 新 `hookScheduler.js`，`app.js` 启动时拉起（与 metricScheduler 并列） | 复用「DB 配置驱动 + node-cron 动态注册 + Redis 锁防多实例并发」的现成模式 |

**边界说明（有意为之）**：
- 记录事件只在**已发布 Data API 的 HTTP 调用路径**上触发——API 服务"测试台"里的试写、AI 工具 `bizdata_insert_mock_data` 的直写**不触发**钩子（测试行为不应触发生产钩子）。这与现有 webhook 触发口径一致。
- SSE 只读流不触发（无写操作）。

## 6. 钩子定义与条件过滤

### 6.1 触发配置（表单分区"触发"）

选择事件类型后，动态展示该事件适用的过滤项：

| 过滤级别 | 适用事件 | 形态 |
|---|---|---|
| 对象过滤 | 记录类事件 → 选实体（多选）；API 事件 → 选 API 服务（多选）；定时 → 填 cron | 下拉多选（数据来自实体/API 服务目录） |
| 操作过滤 | `apiservice.invoked` → 成功/失败/全部 | 单选 |
| 字段变更过滤 | `bizdata.record.updated` → 仅当指定字段变化时触发 | 字段多选（实体字段目录） |
| 表达式条件（进阶，可选） | 所有事件 | 一行 JS 布尔表达式，如 `payload.after.amount > 10000`；在沙箱内求值，异常视为不匹配（skip 并记录） |

**求值顺序**：对象 → 操作 → 字段 → 表达式，由宽到严，廉价过滤在前。所有匹配在**内存缓存的钩子注册表**上完成（§11）。

### 6.2 状态机

```
draft ──启用──▶ enabled ──禁用──▶ disabled
                   │                 │
                   ▼（连续失败达阈值）  └──启用──▶ enabled
              auto_disabled ──人工修复后启用──▶ enabled
```

`auto_disabled` 与 `disabled` 共用"不执行"语义，但列表上以醒目标签区分"系统自动停用（需检查）"。

## 7. 动作类型设计

### 7.1 `http_request` —— 调用外部 HTTP（收编自 outbound webhook）

完整继承现有「提交外部 API」能力，迁移映射见 §16：

- Method（POST/PUT/PATCH）+ URL + Header
- Body 模板：支持 `{{event.after.amount}}` 形式的**事件负载插值**（替代原 transform_script 的最常用场景；transform 脚本作为高级选项保留）
- 可选鉴权：`none` / `bearer` / `api_key`（密钥加密落库、掩码回显、空提交保留）
- 响应判定规则：成功/异常 Schema + 规则（如 `code != 200` 判失败；非 2xx 亦判失败）
- 复用 `outboundHttpClient.js`、`outboundResponseRules.js`、`encryption.js`

### 7.2 `internal_api` —— 调用内部已发布 API 服务

- 选择一个已发布的 API 服务 + operation，参数支持同样的 `{{event.*}}` 插值
- 执行走 `apiServiceExecutionService`（系统身份，跳过 HTTP 层）；执行产生的新事件照常分发（受 §8.4 递归保护约束）
- 用途示例：定时钩子每天调一次"汇总查询 API"，结果再由脚本钩子加工——无需写代码即可串起数据管道

### 7.3 `script` —— 执行 TypeScript 脚本（进阶）

- 脚本签名：`async function handler(event, ctx)`，`return` 值作为输出存入 Run
- **完全复用现有沙箱设施**：
  - 运行时：`apiServiceHandlerRuntime.js` 同款 Node `vm` 沙箱（新栈、白名单全局、默认 5s 超时、Promise 竞速限时）
  - DB 访问：仅通过 `handlerSdk.js` 受控 SDK（列名/操作符白名单校验），脚本拿不到裸 SQL 连接
  - TS 支持：`stripTypeScriptForVm.js` 剥离类型语法后执行；保存前经 `handlerTypeCheck.js`（typescript 包 `ts.createProgram`）做真类型检查，并为 Monaco 提供 `hookSdk.d.ts` 类型提示
- `ctx` 提供：`ctx.log()`（写入 Run 日志）、`ctx.logger`；**第一期不提供网络与文件访问**
- 源码长度上限沿用 20000 字符惯例；输出序列化上限 50000 字符（超出截断并标注）

### 7.4 动作公共配置

| 配置 | 默认 | 说明 |
|---|---|---|
| 超时 | 脚本 5s / HTTP 30s | 可调，脚本上限 30s，HTTP 上限 60s |
| 失败重试次数 | 2 | 指数退避（1s/4s/16s…），超时视为失败 |
| 失败后是否继续重试计数 | 连续 10 次失败自动停用 | 见 §8.3 |
| 执行并发上限 | 3 | 同一钩子同时最多 3 个运行，超出排队（防止慢钩子堆积） |

## 8. 执行引擎与可靠性

### 8.1 异步非阻塞

- `emit()` 内部：匹配钩子 → 逐个投递到**进程内执行队列**（`setImmediate` + 并发闸）→ 立即返回
- 主请求路径上**零 await**（这是对现有 webhook `await` 外呼行为的修正）
- 队列全局并发上限（默认 20），防事件风暴打满进程

### 8.2 运行状态

`success` / `failed` / `timeout` / `skipped`（条件不匹配或递归拦截，便于排查"为什么没触发"）

### 8.3 重试与自动停用

- 失败 → 按退避重试，每次 attempt 都落 Run（同一 `run_group_id` 关联）
- 连续失败计数达阈值（默认 10）→ 状态置 `auto_disabled`，Run 写入停用原因
- 重新启用时清零计数

### 8.4 递归（循环触发）保护

- 每个事件负载携带 `depth`（首发为 0）；钩子动作引起的后续事件（如 internal_api 又写了记录）`depth+1`
- `depth ≥ 3` 时：不执行、记 `skipped`、错误信息"疑似循环触发已拦截"
- 这使"钩子链"可以安全存在（A 调 API → API 触发 B），但不可能无限循环

### 8.5 幂等与去重（轻量实现）

- Run 记录 `event_id`（事件唯一 ID）；同一 `event_id + hook_id` 重复投递时去重（防分发层意外重入）
- 外部系统侧幂等（如重复通知的语义处理）由用户在动作/脚本层自行设计，文档中给出建议示例

## 9. 运行历史与可观测性

- 表：`automation.hook_runs`（§12 DDL），按钩子查询、按状态筛选
- Run 详情页展示：事件 payload（JSON 折叠树）、动作配置快照、每次 attempt 的输出/错误/耗时、日志（脚本 `ctx.log`）
- **重放**：任意 Run 可"用原 payload 重跑"（产生新 Run，标记来源 `replay`）
- **保留策略**：默认保留 30 天且每钩子最近 1000 条；`hookScheduler` 附带每日清理任务（复用调度器模式）
- 列表页聚合展示：最近运行状态、近 7 天成功率（失败率高红色标记）
- 失败告警通道（邮件/站内信）第一期不做，以 `auto_disabled` + 列表醒目标记替代，列入后续演进

## 10. 安全与权限

| 面 | 措施 |
|---|---|
| 脚本沙箱 | Node `vm` 新上下文 + 全局白名单 + 超时；无 `require`/`process`/`fetch`/文件系统 |
| DB 访问 | 仅 `handlerSdk` 白名单操作符与已建模字段；与 API 服务 Handler 同一受控面 |
| 外呼密钥 | AES 加密落库（复用 `encryption.js`）；编辑回显掩码；空提交保留旧值；Run 中绝不记录密钥 |
| Run 数据脱敏 | payload/输出全量存储以便重放；文档明示"勿在脚本中打印密钥"；后续可加字段级脱敏规则 |
| 权限 | 管理路由挂 `auth`（+ 按需登记 builtinApi catalog）；菜单随「API 服务」分组既有权限码 `api_services:manage` |
| 审计 | `created_by` / `updated_by`；所有管理操作可追溯；测试运行与正式运行在 Run 中区分标记 |
| SSRF | 外呼复用 `httpRequestToolService` 的私网/元数据 IP 黑名单策略（现有实现） |

## 11. 性能设计

| 关注点 | 方案 |
|---|---|
| 事件路径开销 | 钩子注册表**内存缓存**：启动全量加载 `enabled` 钩子；任何 CRUD/启停操作失效并重建。事件路径只查内存，零 DB 查询 |
| 无钩子时开销 | 缓存为空 → `emit()` 直接返回（一次 Map lookup） |
| 异步执行 | 进程内队列 + 全局并发上限 20 + 单钩子并发上限 3；超限排队而非丢弃 |
| 匹配成本 | 过滤条件在加载时预编译（实体集合转 Set、表达式预 parse），匹配为纯内存计算 |
| 负载体积 | 事件负载裁剪：请求/响应摘要截断（如 8KB），全文场景引导用户在脚本内按需取数 |

## 12. 数据库设计（DDL 草案）

新增独立 schema `automation`（与 `eadaf`/`aibase`/`bizdata` 平级）。迁移文件：`backend/scripts/migrate-hook-center.sql`（幂等，`CREATE SCHEMA IF NOT EXISTS` / `CREATE TABLE IF NOT EXISTS`），并挂载进 `initdb.sh` 增量迁移段。

```sql
CREATE SCHEMA IF NOT EXISTS automation;

CREATE TABLE IF NOT EXISTS automation.hooks (
    id                   UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name                 VARCHAR(255) NOT NULL,
    description          TEXT,
    status               VARCHAR(32)  NOT NULL DEFAULT 'draft',   -- draft|enabled|disabled|auto_disabled
    event_type           VARCHAR(64)  NOT NULL,                   -- auth.user.login | bizdata.record.* | apiservice.invoked | schedule.cron
    event_filter         JSONB        NOT NULL DEFAULT '{}'::jsonb,  -- {entityCodes?, apiServiceIds?, operations?, changedFields?, cron?}
    condition_expr       TEXT,                                      -- 可选 JS 布尔表达式
    action_type          VARCHAR(32)  NOT NULL,                   -- http_request|internal_api|script
    action_config        JSONB        NOT NULL DEFAULT '{}'::jsonb,  -- 动作差异化配置（含加密密钥字段 auth_secret_enc）
    failure_policy       JSONB        NOT NULL DEFAULT '{}'::jsonb,  -- {retry?, timeoutMs?, concurrency?, disableThreshold?}
    consecutive_failures INT          NOT NULL DEFAULT 0,
    version              INT          NOT NULL DEFAULT 1,
    created_by           VARCHAR(64),
    updated_by           VARCHAR(64),
    created_at           TIMESTAMPTZ  DEFAULT CURRENT_TIMESTAMP,
    updated_at           TIMESTAMPTZ,
    CONSTRAINT hooks_status_chk CHECK (status IN ('draft','enabled','disabled','auto_disabled')),
    CONSTRAINT hooks_action_type_chk CHECK (action_type IN ('http_request','internal_api','script'))
);
CREATE INDEX IF NOT EXISTS hooks_status_event_idx ON automation.hooks (status, event_type);

CREATE TABLE IF NOT EXISTS automation.hook_runs (
    id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    run_group_id   UUID         NOT NULL,          -- 同一次触发的多次 attempt 关联
    hook_id        UUID         NOT NULL REFERENCES automation.hooks(id) ON DELETE CASCADE,
    event_id       UUID         NOT NULL,          -- 事件唯一 ID（去重/重放）
    event_type     VARCHAR(64)  NOT NULL,
    event_depth    INT          NOT NULL DEFAULT 0,
    trigger_source VARCHAR(32)  NOT NULL DEFAULT 'event',  -- event|test|replay|schedule
    payload        JSONB        NOT NULL,
    status         VARCHAR(32)  NOT NULL,          -- success|failed|timeout|skipped
    attempt        INT          NOT NULL DEFAULT 1,
    duration_ms    INT,
    error          TEXT,
    output         JSONB,
    logs           JSONB,                           -- 脚本 ctx.log 输出
    started_at     TIMESTAMPTZ  NOT NULL DEFAULT CURRENT_TIMESTAMP,
    finished_at    TIMESTAMPTZ
);
CREATE INDEX IF NOT EXISTS hook_runs_hook_time_idx  ON automation.hook_runs (hook_id, started_at DESC);
CREATE INDEX IF NOT EXISTS hook_runs_status_idx     ON automation.hook_runs (status, started_at DESC);
CREATE UNIQUE INDEX IF NOT EXISTS hook_runs_dedup_idx ON automation.hook_runs (event_id, hook_id, attempt);
```

配套：Sequelize 模型 `backend/src/models/automation_hook.js`、`automation_hook_run.js`，注册进 `models/index.js`（仓库惯例）。

## 18. 风险与开放问题

| # | 风险/问题 | 应对 |
|---|---|---|
| 1 | **进程内队列在进程重启时丢失未执行任务**（第一期接受）：异步执行尚未落 Run 即崩溃则丢 | 文档明示边界；后续演进：落库 outbox 表 + 启动重放，或引入轻量持久化队列 |
| 2 | 多实例部署时内存缓存一致性（A 实例改钩子，B 实例缓存旧） | 第一期单实例假设；多实例前用 Redis pub/sub 广播失效（Redis 已在栈内） |
| 3 | 事件负载含敏感字段全量入库 | 文档明示 + 后续字段级脱敏规则（开放问题） |
| 4 | 表达式条件书写错误导致永不触发 | 保存时静态校验 + 试跑面板展示"条件是否匹配"（skipped 可见） |
| 5 | 钩子风暴（大量事件 × 大量钩子） | 全局/单钩子并发上限 + 队列深度告警日志；极端场景后续加节流配置 |
| 6 | cron 钩子时区 | 统一服务器时区，配置页明示；多时区需求列开放问题 |
| 7 | webhook 迁移期的双触发风险 | 迁移脚本执行时先禁用旧 webhook 再启用对应新钩子（同一事务内），触发点本就同源不会双发 |
| 8 | 脚本沙箱为 vm 级隔离（非容器级），理论上存在逃逸面 | 与 API 服务 Handler 同风险水位（既有接受）；高危场景后续可切独立 worker 进程 |

**开放问题（留待评审时定）**：
- [ ] 失败告警通知通道（邮件/站内信/ webhook 到运维群）何时做、走什么通道
- [ ] `internal_api` 动作是否允许以"触发者用户身份"执行（当前设计为系统身份）
- [ ] Run 保留策略是否需要按钩子粒度可配
