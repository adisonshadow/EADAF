## 背景

本文件用于描述 AIBase 的成熟闭环执行方法、以及结构化终止/自动续调改造的工程落地；同时补充一个用户可感知的过程态输出目标（类似 Cursor 的 `Planning next moves`）。

1. AI 在输出过程中，支持类似 Cursor 的 `Planning next moves` 效果
2. 用一个明确的 TODO 清单，区分哪些已经完成，哪些仍待实现

---

## 一句话目标

把 AIBase 从“文本驱动的自动续跑”升级为“结构化任务驱动的成熟闭环 Agent”，同时在输出体验上加入可感知的计划推进视图，让用户能看到 AI 当前准备做什么、已经做了什么、接下来还要做什么。

---

## 总体设计

### 1. 执行内核：成熟闭环

底层执行模型采用六阶段状态机：

```text
[接收] -> [勘察] -> [规划] -> [执行] -> [验收] -> [交付]
   ^                                  |
   +-------------- 回退 ---------------+
```

关键约束：

- 不允许靠自然语言“感觉已经完成”来结束
- 每一轮都要能回答：当前目标是什么、现在在做哪一步、这一步是否已经验收通过
- 写操作与查询操作必须区分终止语义

### 2. 工程落地：结构化终止

AIBase 当前的主线落地机制是：

- `update_plan`：维护当前权威任务清单
- `task_complete`：显式声明任务完成并触发终止校验
- `reconcilePlan()`：每轮根据 Tool 结果自动对账计划状态
- `decideStructuredTermination()`：在 text-only round 时判断是终止、继续、还是硬停止

### 3. 查询型任务的轻量闭环

查询/只读任务不能照搬写操作闭环。

例如用户说“列出所有成员”，其合理闭环应当是：

1. 理解用户意图：目标是拿到成员列表
2. 规划为一个极小任务：调用查询 Tool 获取列表
3. 若调用失败，允许自动重试或调整路径
4. 一旦结果已经足够回答问题，则直接进入验收与交付
5. 停止，而不是再开启下一轮执行

因此，查询型任务需要支持“交付即终止”的例外语义。

## Planning next moves 目标

### 想要的效果

在 AI 输出内容过程中，用户不只是看到最终答案或 Tool 结果，还能看到一个类似 Cursor 的轻量计划面板，例如：

```text
Planning next moves
- 重试查询成员列表
- 校验返回结果是否完整
- 汇总成员信息并结束
```

这个信息不是最终交付内容，而是 AI 当前内部推进状态的可视化。

### 价值

- 让用户知道 AI 不是“卡住了”，而是在推进某个明确步骤
- 让用户更容易识别 AI 是否跑偏
- 当 AI 自动重试或多轮执行时，减少“为什么又继续说话了”的困惑
- 与结构化 Plan 一致，让“内部计划”与“外部展示”对齐

### 与现有能力的关系

当前 AIBase 已有以下相关基础设施：

- `update_plan`：已经有结构化任务清单
- `assistantSegments`：已经支持多段消息/工具步骤顺序渲染
- `buildStructuredNudge()`：已经能基于剩余 Plan 生成下一步推动信息

因此，`Planning next moves` 不需要另起一套状态，只需要把现有 Plan 与轮次决策以更友好的 UI 形式暴露出来。

### 推荐实现方式

建议新增一种面向 UI 的轻量段类型，例如：

```ts
type AssistantSegment =
  | { kind: 'text'; ... }
  | { kind: 'tool'; ... }
  | { kind: 'planning'; title: string; items: Array<{ label: string; status: 'pending' | 'in_progress' | 'completed' }> };
```

推荐触发时机：

1. 用户消息刚进入执行循环后，第一次 `update_plan` 完成时
2. 每轮 `reconcilePlan()` 之后
3. 自动重试前
4. `task_complete` 前

推荐展示内容：

- `Planning next moves` 标题
- 当前 `in_progress` 项
- 后续 `pending` 项
- 已完成项可折叠或简略显示

推荐展示原则：

- 只显示 1-3 条最相关步骤
- 不把全部系统提示词泄露给用户
- 不替代最终答案，只作为过程态信息
- 查询型任务最多显示一个极小计划，避免为了展示效果而把简单任务人为复杂化

## 结论

AIBase 当前已经完成了“从简单 auto-continue 向结构化闭环迁移”的关键地基，但用户体验层面还缺一个重要拼图：把内部 Plan 以 `Planning next moves` 的形式暴露出来。

这样做的意义不是“更好看”，而是把 Agent 的内部状态从黑盒变成半透明：

- 对用户来说，看得到 AI 正准备做什么
- 对研发来说，更容易排查为什么停、为什么继续、为什么重复
- 对产品来说，更接近 Cursor 这类成熟 Agent 的过程体验

## 与成熟闭环方法论保持一致（成熟闭环阶段说明）

业界做得好的 Agent（Cursor、Claude Code、Devin、OpenHands 等），本质上都在解决同一个问题：**如何让 Agent 在不确定的环境中，稳定地推进一个复杂任务直到完成，既不提前放弃，也不无限循环。**
下面是一套经过工程验证的完整执行流程，按阶段拆解，每个阶段都有明确的入口条件、核心动作、出口判定和异常路径。
---

## 整体架构：六阶段状态机

```
[接收] → [勘察] → [规划] → [执行] → [验收] → [交付]
   ↑                              │
   └──────── 回退 ────────────────┘
```

**核心设计原则**：每个阶段都是一个**有明确出口条件的状态**，Agent 不能凭"感觉"跳阶段，必须满足出口条件才能进入下一阶段。状态转换由结构化判定驱动，不由模型自然语言决定。
---

## 阶段 0：任务接收与意图解析（Intake）

### 目标

把用户模糊的自然语言需求，转化为**结构化的任务规约（Task Spec）**，作为后续所有阶段的唯一真相源（Single Source of Truth）。

### 核心动作

**1. 需求解构**

将用户输入拆解为三个维度：

- **目标（What）**：最终要达成什么，成功的定义是什么
- **约束（Constraints）**：不能做什么、必须用什么技术栈、时间/资源限制
- **上下文（Context）**：背景信息、相关文件、已有方案、用户偏好

**2. 歧义检测与澄清**

检测需求中的模糊点，优先级排序：

- 🔴 阻塞级：不澄清就无法推进（比如"优化一下那个页面"——哪个页面？）
- 🟡 重要级：影响方案选择但不影响启动（比如"性能要好"——好到什么程度？）
- 🟢 可假设级：可以先做合理假设，后续验证（比如默认用 TypeScript）

**3. 任务规约生成（Task Spec）**

输出结构化的任务规约，包含：

```
TaskSpec {
  goal: string           // 一句话目标
  success_criteria: []   // 可验证的成功标准（3-7条）
  constraints: []        // 硬约束
  assumptions: []        // 做出的假设（用户可推翻）
  scope_in: []           // 明确在范围内的
  scope_out: []          // 明确不在范围内的（防止范围蔓延）
  priority: "high|med|low"
}
```

### 出口条件

- ✅ 所有 🔴 阻塞级歧义已澄清或做出明确假设
- ✅ 成功标准（success_criteria）全部可验证（不是"做好""优化"这种模糊词）
- ✅ 用户已确认（或 Agent 已声明假设并等待用户推翻）

### 异常路径

- 需求过于模糊 → 主动追问，最多追问 2-3 轮，仍模糊则按最小可行范围启动
- 需求包含多个独立任务 → 拆分为多个 TaskSpec，逐个处理

## 阶段 1：现状勘察（Reconnaissance）

### 目标

在动手改任何东西之前，**全面了解当前状态**，避免"盲人摸象"式开发。这是很多 AutoGPT 类 Agent 跳过的阶段，也是它们频繁翻车的根本原因。

### 核心动作

**1. 代码/文件结构测绘**

- 扫描项目目录结构，建立文件地图
- 识别技术栈、框架、构建工具、依赖版本
- 找到与任务相关的核心文件入口

**2. 相关代码精读**

- 定位与任务直接相关的模块/函数/组件
- 理解现有实现逻辑、数据流、调用关系
- 识别潜在的耦合点和影响范围

**3. 运行状态确认**

- 项目能否正常构建/运行
- 现有测试是否通过（建立基线）
- 开发环境是否齐备

**4. 风险与约束发现**

- 有没有奇怪的历史包袱、hack 代码
- 有没有必须遵守的代码规范/模式
- 有没有外部依赖/API 的限制

### 出口条件

- ✅ 已定位所有需要修改的文件和模块
- ✅ 理解了现有实现的核心逻辑
- ✅ 建立了可工作的基线（能跑、测试通过）
- ✅ 识别了主要风险点和影响范围

### 异常路径

- 项目跑不起来 → 先解决环境问题，或将其标记为已知风险
- 代码过于复杂/陌生 → 增加勘察深度，或缩小任务范围
- 发现需求与现状严重冲突 → 回到阶段 0，重新协商任务范围
---

## 阶段 2：方案规划与任务拆解（Planning）

### 目标

将 TaskSpec 转化为**可执行的任务清单（Execution Plan）**，明确每一步做什么、为什么做、怎么验证。

### 核心动作

**1. 方案设计**

- 基于勘察结果，设计实现方案
- 对复杂任务，考虑 2-3 个备选方案，对比优劣
- 选择最优方案并说明理由

**2. 任务拆解（WBS）**

将方案拆解为有序的任务列表，每个任务满足：

- **原子性**：一个任务只做一件事，完成标准明确
- **可验证**：每个任务有对应的验证方法
- **有序性**：明确依赖关系，按执行顺序排列

```
Task {
  id: string
  description: string        // 做什么
  rationale: string          // 为什么要做
  depends_on: [id]           // 依赖哪些任务
  files_involved: []         // 涉及哪些文件
  verification: string       // 怎么验证完成了
  status: "pending|in_progress|completed|skipped|failed"
  risk: "low|med|high"       // 风险等级
}
```

**3. 风险预案**

- 识别高风险任务，提前想好备选方案
- 定义回退策略：如果某步走不通，怎么退、退到哪

**4. 影响评估**

- 预估工作量/迭代轮次
- 评估对其他模块的影响
- 判断是否需要用户中途确认（比如大的架构变更）

### 出口条件

- ✅ 任务清单完整，覆盖所有成功标准
- ✅ 每个任务都有明确的验证方法
- ✅ 依赖关系清晰，执行顺序合理
- ✅ 高风险点有预案

### 异常路径

- 发现方案不可行 → 回到阶段 1 重新勘察，或换备选方案
- 任务过于庞大（>15 个子任务） → 拆分为多个阶段，先做第一阶段
- 需要用户确认方案 → 暂停，输出方案文档等待确认
---

## 阶段 3：执行循环（Execution Loop）

这是 Agent 的核心主循环，也是最容易失控的地方。成熟的实现采用**"单步推进 + 每轮对账"**的模式。

### 循环结构

```
while 还有未完成的任务:
    1. 状态对账（Reconcile）
    2. 选取当前任务
    3. 执行子步骤（Read → Modify → Verify）
    4. 更新任务状态
    5. 检查终止条件
```

#### 3.1 状态对账（每轮必做）
**这是防止失控的最关键一步，绝对不能省。**

每轮循环开始时，强制做：

1. 回顾任务清单，标记已完成的任务
2. 确认当前应该推进哪个任务
3. 检查有没有被遗忘的任务
4. 对齐当前进度与整体目标

> **为什么重要**：LLM 有"注意力漂移"问题——做着做着就忘了原来的目标，或者重复做已经做过的事。强制对账就是给模型一个"锚点"。

#### 3.2 单任务执行的标准三步曲

每个任务内部，严格遵循 **Read → Modify → Verify** 的模式：

**Read（读）**

- 读取需要修改的文件的最新内容
- 确认当前状态与预期一致（防止并发修改、缓存过期）
- 定位具体的修改点

**Modify（改）**

- 实施具体的代码/文件修改
- 遵循最小改动原则，不做无关的"顺手优化"
- 一次只改一个逻辑单元，避免大批量修改难以回退

**Verify（验）**

- 立即验证刚才的修改是否正确
- 验证方式：语法检查、lint、单元测试、手动运行、类型检查等
- 验证不通过 → 修复或回退，不能带着错误前进

#### 3.3 进度更新与反馈

- 每完成一个任务，更新任务状态
- 输出简短的进度摘要（做了什么、结果如何、下一步做什么）
- 遇到问题时，说明问题、尝试过的方案、当前状态

### 循环控制机制

**防提前终止**：

- 任务清单未全部完成 → 不允许终止
- 每个任务必须通过验证才能标记完成
- 禁止"我觉得差不多了"式的主观终止

**防无限循环**：

- 最大迭代轮次限制（比如 50 轮）
- 同一错误连续出现 3 次 → 标记为阻塞，停止尝试
- 同一任务耗时超过预估 3 倍 → 触发反思，检查是否走错方向
- 全局时间/Token 预算限制

**反思触发点**：

遇到以下情况强制暂停反思：

- 连续失败/重试
- 任务进度严重滞后
- 发现之前的假设有误
- 出现意料之外的复杂情况

反思输出：问题诊断 + 调整方案 + 是否需要用户介入

### 出口条件

- ✅ 所有任务标记为 completed
- ✅ 每个任务的验证都通过
- ✅ 没有遗留的错误或警告

### 查询型任务的轻量闭环

- 对“列出列表 / 查看详情 / 检索信息”这类**只读任务**，规划结果可以收敛为 1 个极小任务：获取并核对所需数据
- 当查询 Tool 成功返回，且结果已经足以直接回答用户问题时，**应视为已达到执行目标**
- 这类任务完成后应直接进入验收与交付，**不应为了形式继续补下一轮执行**
- 若查询过程中出现错误（如 500 / 权限 / 参数问题），Agent 可以在执行阶段自行重试、换工具或调整路径；只要最终目标达成并验收合格，即可结束

### 异常路径

- 遇到阻塞且无法自行解决 → 暂停执行，向用户报告阻塞原因和已尝试的方案
- 发现规划有误 → 回到阶段 2 重新规划，更新任务清单
- 范围蔓延（发现需要做更多的事） → 评估是否在原范围内，超出则与用户确认
---

## 阶段 4：验收与验证（Verification & Validation）

### 目标

从**整体层面**验证任务是否真的完成了，而不只是每个步骤都做完了。这是"做完"和"做好"的区别。

### 核心动作

**1. 功能验收（对应 success_criteria）**

逐条验证 TaskSpec 中的成功标准：

- 每条标准都要有对应的验证操作和结果
- 不能靠"应该可以"，必须实际验证
- 记录验证结果（通过/失败/部分通过）

**2. 回归测试**

- 运行完整的测试套件，确保没有引入新问题
- 检查相关功能是否受影响
- 对比修改前后的行为差异

**3. 代码质量检查**

- 代码风格/规范是否符合项目要求
- 有没有遗漏的错误处理、边界情况
- 有没有调试代码、临时文件需要清理
- 性能/安全有没有明显问题

**4. 文档同步**

- 需要更新的文档是否更新了
- 注释是否完整准确
- 变更记录（Changelog）是否需要补充

### 出口条件

- ✅ 所有成功标准验证通过
- ✅ 回归测试全部通过
- ✅ 没有遗留的临时代码/调试代码
- ✅ 文档已同步更新

### 异常路径

- 验收不通过 → 回到阶段 3，新增修复任务
- 发现重大问题需要返工 → 评估返工范围，必要时回到规划阶段
- 部分标准无法验证 → 说明原因，由用户确认是否接受
---

## 阶段 5：收尾与交付（Finalization）

### 目标

干净利落地结束任务，给用户一个清晰的交付总结。

### 核心动作

**1. 清理**

- 删除临时文件、调试代码
- 恢复不需要保留的修改
- 清理缓存、构建产物等

**2. 最终验证**

- 最后跑一遍完整的构建/测试
- 确认最终状态是干净的、可工作的

**3. 交付总结**

输出结构化的交付报告：

- 做了什么（变更摘要）
- 怎么做的（方案简述）
- 验证结果（验收情况）
- 注意事项（已知限制、后续建议）
- 涉及的文件列表

### 出口条件

- ✅ 所有清理工作完成
- ✅ 最终验证通过
- ✅ 交付总结已输出
---

## 贯穿全流程的关键机制

### 1. 上下文管理策略

**优先级分层**（高 → 低，低优先级的优先裁剪）：

1. 🟥 TaskSpec（任务规约）—— 永远保留
2. 🟥 Task List（任务清单 + 当前状态）—— 永远保留
3. 🟧 当前任务相关的文件内容
4. 🟧 最近几轮的执行记录
5. 🟨 历史执行记录（可摘要）
6. 🟩 勘察阶段的详细信息（可摘要）
7. ⬜ 更早的对话历史（优先裁剪）

**动态压缩**：

- 已完成的任务，详细执行过程压缩为摘要
- 读过的文件，如果不再需要，只保留路径和关键结论
- 旧的工具输出，只保留最终结果，丢弃中间过程

### 2. 错误处理与恢复

**错误分级**：

- 轻微错误（比如 typo） → 立即修复，继续执行
- 中等错误（比如逻辑 bug） → 修复后验证，记录到任务日志
- 严重错误（比如方案走不通） → 触发反思，考虑回退或换方案
- 阻塞错误（比如缺权限、环境问题） → 暂停，请求用户介入

**回退机制**：

- 每个任务开始前，记录当前状态（文件快照/git commit）
- 任务失败时，可以快速回退到任务开始前的状态
- 避免"越改越乱"的雪崩效应

### 3. 用户介入点

设计明确的用户介入时机，而不是让用户一直等：

- 任务开始前：确认方案（复杂任务）
- 执行中：遇到阻塞、需要决策、范围变更
- 验收后：交付结果，等待反馈
- 异常时：及时报告，不闷头死磕

## 与你现有 auto continue 的对比

| 维度 | 简单 auto continue | 成熟执行流程 |
|------|-------------------|-------------|
| 驱动方式 | 关键词检测 + 外部续跑 | 结构化状态机驱动 |
| 终止判定 | 模型自然语言 + 关键词 | 三层判定（任务完成 + 验收通过 + 整体对齐） |
| 进度管理 | 无，全靠模型记忆 | 结构化任务清单，每轮对账 |
| 防失控 | 最大轮次兜底 | 多维度控制（轮次/错误/进度/预算） |
| 质量保障 | 无 | 每步验证 + 最终验收 + 回归测试 |
| 上下文 | 自然衰减 | 分层管理 + 动态压缩 |

3. 实现三层终止判定
4. 最后再补勘察、验收、上下文管理等进阶能力
