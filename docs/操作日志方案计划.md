# 操作日志（Operation Audit Log）功能方案计划

> 状态：**待审阅**（本文档为方案计划，尚未实施）
> 日期：2026-09-01
> 产品入口：**系统 → 操作日志**（`/system/operation-logs`）
> 关联文档：[钩子管理方案计划.md](./钩子管理方案计划.md)（调度器/清单模式参照）、[p2-observability.md](./improvements/p2-observability.md)（AI 可观测性，互补不重叠）

---

## 1. 背景与目标

EADAF 是多角色的企业级底座（IAM、SSO、业务数据建模与物化、API 服务、AI 编排、钩子中心），但**"谁在什么时候对什么做了什么"目前几乎不可追溯**：

- `uac.operation_logs` 表已存在，但只有 7 处零散写入（详见 §3.2），**没有任何查询 API 和前端页面**——写进去的日志 nobody can see；
- 除用户/角色管理外的所有管理域（部门、权限、应用、业务数据、API 服务、AI 配置、存储、钩子、系统设置）**完全不写操作日志**；
- 一旦出现"数据被误删 / 配置被误改 / 密钥被重置"这类事件，无法回答最基本的审计问题。

本方案一次性补齐三件事：

1. **记录**：以统一的混合式机制覆盖全部管理域的写操作（修复现有表结构缺陷）；
2. **查询**：提供分页/筛选/详情的管理端查询 API；
3. **查看**：前端"系统 → 操作日志"页面（列表 + 详情抽屉）。

### 目标用户

- **系统管理员/审计员**：日常巡检、事后追责、合规审计；
- **普通排查者**：通过 trace_id 把一次操作与 AI 请求日志（`ApiRequestLog`）、钩子运行记录（`automation_hook_runs`）串联定位问题。

### 非目标（明确不做）

- ❌ **数据面调用审计**——Data API 执行、AI 对话请求属于运行日志，已有 `aibase.api_request_logs`、`automation_hook_runs`、`outbound_webhook_runs` 各自承载，本功能只管**管理面操作**；
- ❌ **拦截/回滚能力**——操作日志只做事后记录，不支持"撤销某次操作"；
- ❌ 日志防篡改（签名/链式哈希）——企业内部审计场景暂不需要，列入开放问题；
- ❌ 替换 winston 运行日志——两套日志定位不同（排障 vs 审计），互不替代。

## 2. 已确认的产品决策

以下三点已于 2026-09-01 与需求方确认：

| 决策点 | 结论 | 含义 |
|---|---|---|
| 覆盖范围 | **一步到位全覆盖** | 所有管理域一次性接入记录机制（仍按里程碑分批交付代码，见 §14） |
| 访问权限 | **走内置 API 权限体系** | 权限码注册进 `builtinApi/catalog.js`，路由挂 `authWithBuiltinApiGuard`，支持 `uac.builtin_api_configs` 角色/部门级 access_restriction 配置 |
| 记录机制 | **混合式** | 声明式中间件自动记录公共信息（操作者/IP/traceId/耗时/成败）+ 控制器按需手动提供数据快照（old/new），落库收敛到中间件一处 |

## 3. 现状盘点（基于代码核实）

### 3.1 现有日志设施一览

| 设施 | 载体 | 定位 | 有查看入口？ |
|---|---|---|---|
| **OperationLog 操作日志** | `uac.operation_logs`（模型 `backend/src/models/operation_log.js`） | 管理操作审计 | ❌ **无任何读取代码** |
| ApiRequestLog AI 请求日志 | `aibase.api_request_logs` | AI 对话请求 | ✅ `/api/v1/admin/ai-request-logs` + 前端「AI 管理 → 请求日志」 |
| winston 运行日志 | `backend/logs/*.log`（按天滚动） | 进程排障 | 仅服务器文件 |
| login_attempts | `uac.login_attempts` | 登录安全分析 | ❌ |
| 各域运行历史 | `automation_hook_runs`、`outbound_webhook_runs`、`bizdata_*_runs` | 任务执行记录 | 部分（钩子运行历史页面） |

**结论：操作日志是唯一"有写入、零读取"的日志设施，且写入本身覆盖面与质量都不足。** AI 请求日志功能（`adminAiRequestLogRoutes.js` + `aiRequestLogController.js` + 前端 `RequestLogs` 页面）是本功能最完整的现成参照，API/前端设计直接沿用其模式。

### 3.2 operation_logs 现状与缺陷

现有表结构（`backend/scripts/schemas.sql` L178-195）：

```sql
CREATE TABLE uac.operation_logs (
    log_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID,
    operation_type VARCHAR(50) NOT NULL,
    resource_type VARCHAR(50) NOT NULL,
    resource_id VARCHAR(50) NOT NULL,
    old_data JSONB,
    new_data JSONB,
    status VARCHAR(20) NOT NULL DEFAULT 'SUCCESS' CHECK(status IN ('SUCCESS','FAILED','PENDING')),
    error_message TEXT,
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);
```

现有 7 处写入点（全部 inline `try { await OperationLog.create(...) } catch`，写失败仅 winston 记录、不阻断主流程）：

| 位置 | operation_type | resource_type |
|---|---|---|
| `userController.js:254` | UPDATE | user |
| `userController.js:794` | DELETE | user |
| `userController.js:882` | RESTORE | user |
| `userController.js:963` | LOGOUT | user |
| `userController.js:1174` | RESET_PASSWORD | user |
| `roleController.js:245` | UPDATE | role |
| `roleController.js:310` | DELETE | role |

**五个缺陷**（本方案逐一修复）：

| # | 缺陷 | 影响 |
|---|---|---|
| 1 | `user_id` 存的是**被操作的目标用户**而非**操作者**（如管理员 A 改用户 B，`user_id=B`） | 无法回答"谁做的"——审计的核心问题 |
| 2 | 无 IP / User-Agent / trace_id / 耗时 | 无法定位来源、无法与运行日志关联 |
| 3 | `created_at` 无索引 | 时间排序分页查询全表扫描 |
| 4 | 覆盖面只有用户更新/删除/恢复/登出/重置密码 + 角色更新/删除（**连创建都不记**） | 其他所有管理域零审计 |
| 5 | 落库代码散落在各控制器（每处 15+ 行 try/catch 样板） | 难维护、新域接入成本高、易漏记 |

## 4. 核心概念与整体架构

```
 管理请求（写操作）
      │
      ▼
 ┌─────────┐   ┌──────────────────────────────┐
 │  auth    │──▶│ operationAudit 中间件（声明式） │  ← 路由上声明 domain/operationType/resourceType
 └─────────┘   └──────────────┬───────────────┘
                                  │ await next()
                    ┌────────────▼────────────┐
                    │        控制器            │  ← 需要时设置 ctx.state.auditContext：
                    │  （业务逻辑不动）          │     resource_id / resource_name /
                    └────────────┬────────────┘     old_data / new_data（已脱敏）
                                  │ 响应完成
                                  ▼
                    ┌──────────────────────────┐
                    │ 中间件统一落库（异步）       │  操作者(用户/应用令牌) + IP + UA
                    │  SUCCESS / FAILED        │  + traceId + 耗时 + 请求摘要
                    └────────────┬─────────────┘
                                 ▼
                      uac.operation_logs
                                 │
                                 ▼
              GET /api/v1/admin/operation-logs（列表/详情）
                                 │
                                 ▼
              前端「系统 → 操作日志」（UrlSyncedProTable + 详情抽屉）
```

| 概念 | 说明 |
|---|---|
| **操作者 Operator** | 谁发起的操作。三种类型：`USER`（登录用户令牌）、`APPLICATION`（第三方应用令牌，如经内置 API 的应用调用）、`SYSTEM`（内部调度器，预留）。冗余存 `operator_name` 快照，用户被删后仍可显示 |
| **域 Domain** | 操作所属模块，与前端导航/内置 API 清单的域划分对齐（`user`/`role`/`department`/`application`/`bizdata`/`apiservice`/`ai`/`storage`/`automation`/`system`/`auth`），用于筛选与统计 |
| **操作类型 operation_type** | `CREATE`/`UPDATE`/`DELETE`/`RESTORE`/`STATUS_CHANGE`/`RESET_PASSWORD`/`ASSIGN_ROLES`/`ASSIGN_PERMISSIONS`/`PUBLISH`/`UNPUBLISH`/`EXECUTE`/`LOGIN`/`LOGOUT`（全大写，兼容现有数据） |
| **资源 Resource** | 操作对象：`resource_type`（如 `api_service`）+ `resource_id` + `resource_name`（名称快照，列表直接展示） |
| **快照 Snapshot** | `old_data`/`new_data` JSONB，变更前/后数据（敏感字段已剔除），仅详情页展示 |
| **请求摘要 request_summary** | JSONB：`{method, path, statusCode, bodyKeys}`——只存方法/路径/状态码/请求体字段名列表，**不存请求体全文** |

## 5. 数据库设计（DDL 草案）

迁移脚本：`backend/scripts/migrate-operation-log-audit.sql`（幂等，挂入 `initdb.sh`，模式同 `migrate-builtin-api-system.sql`）：

```sql
BEGIN;

-- 操作日志表增强：操作者、资源名、域、请求上下文
ALTER TABLE uac.operation_logs
  ADD COLUMN IF NOT EXISTS operator_id UUID REFERENCES uac.users(user_id),
  ADD COLUMN IF NOT EXISTS operator_name VARCHAR(100),
  ADD COLUMN IF NOT EXISTS operator_type VARCHAR(20) NOT NULL DEFAULT 'USER'
    CHECK (operator_type IN ('USER', 'APPLICATION', 'SYSTEM')),
  ADD COLUMN IF NOT EXISTS resource_name VARCHAR(200),
  ADD COLUMN IF NOT EXISTS domain VARCHAR(50),
  ADD COLUMN IF NOT EXISTS ip VARCHAR(45),          -- 兼容 IPv6 最长 45
  ADD COLUMN IF NOT EXISTS user_agent VARCHAR(500), -- 超长截断
  ADD COLUMN IF NOT EXISTS trace_id VARCHAR(64),
  ADD COLUMN IF NOT EXISTS duration_ms INTEGER,
  ADD COLUMN IF NOT EXISTS request_summary JSONB;

-- 查询路径索引（现状仅有 user_id / (resource_type,resource_id) / status 三个）
CREATE INDEX IF NOT EXISTS idx_operation_logs_created_at
  ON uac.operation_logs (created_at DESC);
CREATE INDEX IF NOT EXISTS idx_operation_logs_operator_id
  ON uac.operation_logs (operator_id);
CREATE INDEX IF NOT EXISTS idx_operation_logs_domain_created_at
  ON uac.operation_logs (domain, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_operation_logs_trace_id
  ON uac.operation_logs (trace_id);

COMMENT ON COLUMN uac.operation_logs.operator_id   IS '操作者用户ID（USER 型）；APPLICATION 型存发起应用对应记录可为空';
COMMENT ON COLUMN uac.operation_logs.operator_name IS '操作者名称快照（用户名/应用名），防用户删除后无法显示';
COMMENT ON COLUMN uac.operation_logs.operator_type IS '操作者类型 USER|APPLICATION|SYSTEM';
COMMENT ON COLUMN uac.operation_logs.resource_name IS '资源名称快照（用户名/服务名等）';
COMMENT ON COLUMN uac.operation_logs.domain        IS '所属模块域（user/role/bizdata/...）';
COMMENT ON COLUMN uac.operation_logs.request_summary IS '请求摘要 {method,path,statusCode,bodyKeys}，不含请求体内容';

COMMIT;
```

要点：

- **不动现有列**，`user_id` 保留并回归其本义——**目标用户**（被操作者）；新增 `operator_*` 表达操作者。对登录/登出这类"自己操作自己"的场景，两者值相同；
- **存量数据**：`operator_id`/`operator_name` 为 NULL，前端显示"—"（历史数据无法可靠推断真实操作者，不做回填）；
- `resource_id` 保持 `VARCHAR(50)` 不变（UUID 36 字符可容纳，兼容非 UUID 资源标识）；
- Sequelize 模型 `models/operation_log.js` 同步新增字段定义（`models/index.js` 已注册，无需改关联）。

## 6. 记录机制设计（混合式）

### 6.1 声明式中间件 `operationAudit`

新增 `backend/src/middlewares/operationAudit.js`，按项目惯例**逐路由挂载**（auth 之后）：

```js
// backend/src/routes/userRoutes.js（示例）
const { operationAudit } = require('../middlewares/operationAudit');

router.put('/:user_id',
  authWithBuiltinApiGuard,
  operationAudit({
    domain: 'user',
    operationType: 'UPDATE',
    resourceType: 'user',
    resourceId: (ctx) => ctx.params.user_id,
    // request_summary 记录的请求体字段名白名单（仅字段名，不含值）
    summaryKeys: ['username', 'email', 'status'],
  }),
  UserController.updateUser
);
```

中间件行为（伪代码）：

```js
function operationAudit(config) {
  return async (ctx, next) => {
    const startAt = Date.now();
    await next();                                   // 业务先行，不影响主流程
    const success = ctx.status < 400;

    const operator = resolveOperator(ctx);          // USER: ctx.state.user；APPLICATION: ctx.state.application；均无 → SYSTEM
    const audit = ctx.state.auditContext || {};     // 控制器手动快照（§6.2），可选

    const record = {
      operator_id:   operator.id ?? null,
      operator_name: operator.name ?? null,
      operator_type: operator.type,
      domain:        config.domain,
      operation_type: config.operationType,
      resource_type: config.resourceType,
      resource_id:   audit.resource_id ?? config.resourceId?.(ctx) ?? '',
      resource_name: audit.resource_name ?? null,
      user_id:       audit.target_user_id ?? null,  // 目标用户（保持现有语义）
      old_data:      audit.old_data ?? null,
      new_data:      audit.new_data ?? null,
      status:        success ? 'SUCCESS' : 'FAILED',
      error_message: success ? null : (ctx.body?.message ?? '').slice(0, 2000),
      ip:            clientIp(ctx),                 // X-Forwarded-For 优先，回退 ctx.ip
      user_agent:    (ctx.get('user-agent') || '').slice(0, 500),
      trace_id:      ctx.state.traceId ?? null,     // 复用现有 traceId 中间件
      duration_ms:   Date.now() - startAt,
      request_summary: {
        method: ctx.method, path: ctx.path,
        statusCode: ctx.status,
        bodyKeys: pickKeys(ctx.request.body, config.summaryKeys),
      },
    };

    setImmediate(() => {                            // 异步落库，不拖慢响应
      OperationLog.create(record).catch((err) =>
        logger.error('写操作日志失败', { path: ctx.path, error: err.message })
      );
    });
  };
}
```

设计取舍：

- **成败判定用 `ctx.status < 400`**，无需控制器配合；错误消息取响应体 `message`（errorHandler 中间件已保证信封格式）；
- **`setImmediate` 异步写入**：管理操作 QPS 极低，不为性能，只为不让日志写库失败/耗时影响响应；代价是进程崩溃瞬间可能丢尾部 1-2 条，审计场景可接受（§15-R5）；
- 写失败仅 winston 记录，**延续现有惯例、永不阻断主流程**；
- `resource_id` 允许为空字符串（表定义 NOT NULL，CREATE 场景资源 ID 在响应体里，由控制器经 auditContext 回填，或声明 `resourceId: (ctx) => ctx.body?.data?.user_id`）。

### 6.2 控制器手动快照 `ctx.state.auditContext`

需要**变更前后数据**或**资源名称**的场景，控制器在业务逻辑中顺手设置（替代现有的 inline 落库样板）：

```js
// userController.updateUser（改造后）
const oldData = redactFields(user.toJSON(), SENSITIVE_USER_FIELDS);  // 变更前快照
await user.update(updateData);
ctx.state.auditContext = {
  resource_id: user.user_id,
  resource_name: user.username,
  target_user_id: user.user_id,
  old_data: oldData,
  new_data: redactFields(user.toJSON(), SENSITIVE_USER_FIELDS),      // 变更后快照
};
ctx.body = { code: 200, message: '更新成功', data: ... };
```

**这是混合式的核心**：中间件负责"统一落库 + 公共上下文"，控制器只负责"它才知道的业务细节"。落库逻辑从 7 处收敛到 1 处，新域接入 = 挂中间件 + （可选）设 auditContext 两行。

### 6.3 现有 7 处写入点的迁移

逐处替换为 `operationAudit` 中间件 + auditContext：

| 现有位置 | 迁移后 | 说明 |
|---|---|---|
| `userController.js:254`（UPDATE） | 路由挂 `operationAudit({domain:'user', operationType:'UPDATE', ...})` + 控制器设快照 | `operation_type`/`resource_type` 值**保持不变** |
| `userController.js:794`（DELETE）、`:882`（RESTORE）、`:963`（LOGOUT）、`:1174`（RESET_PASSWORD） | 同上 | 同上 |
| `roleController.js:245`/`:310` | 同上 | 同上 |

**兼容性约束**：`backend/test/user.test.js`（L306-309 断言 `operation_type: 'UPDATE'`、L552-555 断言 `'LOGOUT'`）等现有测试必须保持通过——迁移不改变这些字段的取值，只改变写入位置；测试中若有对 inline 写入时序的断言（await 完成即落库 → 改为 setImmediate 异步），需要相应等待手段（测试里直接 await 中间件的内部 `flush()` 导出函数，或测试环境改为同步写）。**同步/异步写入通过环境变量 `OPERATION_AUDIT_SYNC=true` 切换**，测试用同步模式保证确定性。

### 6.4 脱敏

新增 `backend/src/utils/redactFields.js`：

```js
const DEFAULT_SENSITIVE_KEYS = ['password', 'secret', 'token', 'app_secret', 'client_secret',
                                'api_key', 'apikey', 'private_key', 'authorization'];
function redactFields(obj, extraKeys = []) { /* 递归剔除匹配键（大小写不敏感），值替换为 '[REDACTED]' */ }
```

- **old_data / new_data 快照必须过 redactFields**——应用密钥、数据库连接密码、SSO client_secret 是本系统最高敏数据；
- request_summary 只存字段名（bodyKeys），天然不泄值；
- 各域的敏感键清单在中间件声明处就近定义（如 `application` 域额外加 `sso_config.secret` 路径）。

## 7. 全域覆盖清单（一步到位）

记录原则：**管理面写操作全记；例行读操作不记；数据面调用不记（归各自运行日志）；手动触发的执行类操作记 `EXECUTE`**。

| 域 domain | 覆盖操作（operation_type） | 主要路由来源 | 快照要求 |
|---|---|---|---|
| `auth` | LOGIN / LOGOUT | `authRoutes.js` | 无（login_attempts 承载失败详情，见 §15-Q2） |
| `user` | CREATE / UPDATE / DELETE / RESTORE / STATUS_CHANGE / RESET_PASSWORD / ASSIGN_ROLES | `userRoutes.js` | old/new（密码剔除）；**补齐目前缺失的 CREATE** |
| `role` | CREATE / UPDATE / DELETE / ASSIGN_PERMISSIONS | `roleRoutes.js` | old/new（补齐缺失的 CREATE/权限分配） |
| `department` | CREATE / UPDATE / DELETE | `departmentRoutes.js` | old/new |
| `permission` | CREATE / UPDATE / DELETE | `permissionRoutes.js` | old/new |
| `application` | CREATE / UPDATE / DELETE / SSO 配置变更 / 密钥重置 | `applicationRoutes.js`、`applicationSsoRoutes.js` | old/new **强制脱敏**（app_secret/client_secret） |
| `bizdata` | 实体 CREATE/UPDATE/DELETE、物化 EXECUTE（手动触发）、数据库连接 CREATE/UPDATE/DELETE、数据标准、元数据管理 | `businessDataRoutes.js` | 连接密码强制脱敏 |
| `apiservice` | CREATE / UPDATE / DELETE / PUBLISH / UNPUBLISH | `apiServiceAdminRoutes.js` | old/new（含 SQL/配置摘要） |
| `ai` | provider/model/scope/tool/skill 的 CREATE/UPDATE/DELETE | `adminProviderRoutes.js` 等 5 个 admin 路由 | 密钥类脱敏 |
| `storage` | bucket CREATE/DELETE/UPDATE、文件 DELETE | `storageRoutes.js` | 资源名必记 |
| `collection` | 采集管道 CREATE/UPDATE/DELETE、手动运行 EXECUTE | `collectionPipelineAdminRoutes.js` | 无快照 |
| `automation` | 钩子 CREATE/UPDATE/DELETE、启用/禁用 STATUS_CHANGE、测试运行 EXECUTE | `automationHookRoutes.js` | 密钥脱敏（http_request 动作的 header/auth） |
| `system` | 系统设置 UPDATE、手动备份 EXECUTE | `systemRoutes.js` | 设置项 old/new |
| （不记） | 数据面：Data API 执行、AI 对话、stream、公开路由、验证码、demo | `apiServiceDataRoutes.js`、`aiRoutes.js` 等 | 归 `ApiRequestLog`/运行历史 |

## 8. 查询 API 设计

## 9. 权限设计

### 9.1 内置 API 清单注册

`backend/src/services/builtinApi/catalog.js` 的 `system` 域下新增（模式同 `ai:request_log:list/get`）：

```js
{
  code: 'system:operation_log:list',
  domain: 'system',
  label: '操作日志列表',
  routePath: '/api/v1/admin/operation-logs',
  httpMethods: ['GET'],
  actions: ['read'],
  description: '查询操作日志列表',
},
{
  code: 'system:operation_log:get',
  domain: 'system',
  label: '操作日志详情',
  routePath: '/api/v1/admin/operation-logs/:log_id',
  httpMethods: ['GET'],
  actions: ['read'],
  description: '查看操作日志详情',
},
```

两条路由挂 `authWithBuiltinApiGuard`（= auth + requireBuiltinApiPermission，见 `middlewares/withBuiltinApiGuard.js`）。

### 9.2 ⚠️ 现有权限机制的一个真缺陷（必须随本功能修复）

核实代码后发现：`assertBuiltinApiAccess`（`builtinApiPermissionService.js` L136-178）对**用户令牌**做角色限制判断时，读取 `ctx.state.user.roleIds`——但登录 JWT payload 只签了 `{user_id, username}`（`authController.js` L245），`auth.js` 中间件也**不补充任何角色信息**（全文无 roleIds 相关代码）。

**后果：对用户令牌，`uac.builtin_api_configs` 一旦配置 `mode:'role'`，`roleIds` 恒为空数组 → 所有登录用户（包括 SUPER_ADMIN）都会被 403**。也就是说当前内置权限体系对用户令牌实际只有"全放（未配置）/全禁（配置了角色限制）"两种状态。

**修复方案（随 M2 落地，收益不限于本功能）**：`assertBuiltinApiAccess` 在用户令牌且 `ctx.state.user.roleIds` 缺失时，回查数据库 `user_roles → roles`（带 60 秒内存缓存，user_id → roleIds），再执行角色比对；同时在比对中放行 SUPER_ADMIN 角色 code。改动集中在 `builtinApiPermissionService.js` 一个文件。

### 9.3 初始权限配置（seed）

`backend/scripts/eadaf-permissions-catalog-seed.sql` 追加：

```sql
-- 菜单权限：系统管理分组（当前 /system 无权限记录=默认放行，补齐后走 access_restriction 过滤）
INSERT INTO uac.permissions (permission_id, code, description, resource_type, actions, status, created_at, updated_at)
VALUES ('660e8400-e29b-41d4-a716-446655440090', 'system:manage', '系统管理', 'MENU', '["read"]', 'ACTIVE', CURRENT_TIMESTAMP, CURRENT_TIMESTAMP)
ON CONFLICT (code) DO UPDATE SET description = EXCLUDED.description, updated_at = CURRENT_TIMESTAMP;
```

配套 `migrate-operation-log-audit.sql` 中：

```sql
-- 查询权限默认限 SUPER_ADMIN（依赖 §9.2 的角色回查修复）；无需收紧可删除此行（回到"登录即可见"）
INSERT INTO uac.builtin_api_configs (code, access_restriction) VALUES
  ('system:operation_log:list', '{"mode":"role","roleIds":["<SUPER_ADMIN_ROLE_ID>"]}'::jsonb),
  ('system:operation_log:get',  '{"mode":"role","roleIds":["<SUPER_ADMIN_ROLE_ID>"]}'::jsonb)
ON CONFLICT (code) DO UPDATE SET access_restriction = EXCLUDED.access_restriction;
```

（SUPER_ADMIN 角色 ID 取自 `scripts/superadmin.sql` 种子，实施时固定为常量。）

前端菜单侧无 §9.2 问题：`isMenuAllowed()`（`frontend/src/routes/config.ts` L95）用 `/me` 返回的角色 + `isSuperAdmin()` 旁路 + `access_restriction` 三者判定，体系完整。

### 9.4 权限生效矩阵（修复后）

| 调用主体 | 行为 |
|---|---|
| 前端登录用户（用户令牌） | 按 `builtin_api_configs` 的 role/department 限制；SUPER_ADMIN 放行；未配置 → 任意登录用户可访问（与现有全部 admin 路由一致） |
| EADAF 本系统应用令牌 | 全放行（`application.code === 'EADAF'` 短路，现有逻辑） |
| 第三方应用令牌 | 需 `builtin_api_scope.permissionCodes` 含 `system:operation_log:list` |

## 15. 风险与开放问题

**风险**

- **R1 · 权限收紧依赖回查修复**：不修 §9.2 直接配 role 限制 = 全员 403。M2 已包含修复；若用户审阅时决定"初期登录即可见"，可跳过 seed 中的 `builtin_api_configs` 插入，后续再收紧（见 Q1）。
- **R2 · 中间件挂载遗漏**：混合式仍需逐路由声明，新增管理路由可能忘记挂。缓解：M4 交付时在 `PAGE_LAYOUT_STANDARD` 等价的后端开发约定文档中补一条"新增管理写路由必须挂 operationAudit"；未来可加启动期自检（扫描 admin 路由中未挂中间件的写方法并 warn）。
- **R3 · 快照体积**：大实体（如宽表实体定义）全量快照使 JSONB 膨胀。缓解：快照统一裁剪——只保留顶层标量字段 + 变更字段，超大字段（SQL 正文等）截断至 2KB。
- **R4 · 事务边界**：业务成功但日志失败（或相反）不构成一致性问题——日志写失败仅 winston 留痕；业务失败仍记 FAILED 日志（这正是审计价值）。
- **R5 · 异步写丢失**：进程崩溃瞬间丢尾部 1-2 条日志。审计非强一致场景可接受；不可接受时改队列表（过度设计，不建议）。

**开放问题（请审阅时决策）**

- **Q1 · 初期权限口径**：A. 随 M2 直接收紧到 SUPER_ADMIN（推荐，修复到位后无额外成本）；B. 初期"登录即可见"（与现有全部 admin 路由一致），M5 再收紧。
- **Q2 · 登录失败是否入操作日志**：本方案只记 LOGIN 成功 + LOGOUT，失败详情由 `uac.login_attempts` 承载（防暴力尝试刷量污染审计流）。是否需要失败也进日志流？
- **Q3 · 自动调度操作是否记录**：物化定时调度、钩子定时触发属 SYSTEM 发起，当前方案不记（各域已有运行历史表）。是否需要以 `operator_type='SYSTEM'` 落一条操作日志以获得统一视图？
- **Q4 · 操作日志写入是否触发钩子事件**（如 `system.operation_log.created`）：暂不做（避免与钩子中心形成记录链）；若未来审计告警需求（"有人删用户就通知"）出现，可复用钩子中心事件分发，届时再评估。
- **Q5 · 保留期默认值**：本方案建议 180 天（M5 实现清理任务），是否合适？
