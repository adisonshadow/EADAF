# 04 — 代码运行时（JS / Python）

> 新增能力。对照 Harness Code Mode，但定位为 **业务编排与计算**，不是编程 Agent。

---

## 1. 为什么需要

现有 Agent 只能「串行调业务 Tool」。复杂场景（多结果拼接、条件分支、批量聚合、轻量变换）只能靠多轮 LLM + 工具，贵且易偏。

`run_code` 让模型写一小段脚本，在沙箱中 `await tools.xxx(args)`，**子调用仍走完整 Tool 管线**（校验、权限、信封、Surface）。

---

## 2. 定位与边界

### 是

- 编排已注册 Tool
- 对 Tool 返回的结构化数据做计算 / 过滤 / 汇总
- 减少「为了拼数据而空转的 LLM 轮次」

### 不是

- 不是让 Agent 给业务系统写功能代码并部署
- 不是任意网络爬虫 / 任意读盘写盘
- 不是默认入口：默认仍 **native tools**（业务 Tool schema 对模型可见）

### 与 subagent 的关系

| 能力 | 用途 |
|------|------|
| `run_code` | 同会话内、短脚本编排 |
| `subagent`（MS6） | 隔离上下文的委托、批量 fan-out |

---

## 3. 运行位置（已定）

| 语言 | 浏览器 | 后端 |
|------|--------|------|
| **JavaScript / TypeScript** | Worker（编排 client Tool、纯计算） | `vm` / 受限进程（编排 server Tool） |
| **Python** | 不做 | 子进程沙箱（超时 / 内存上限） |

后端 JS 可复用现有经验：[`apiServiceHandlerRuntime.js`](../../../backend/src/services/apiService/apiServiceHandlerRuntime.js) 的 `runInNewContext` 模式（超时、白名单全局对象）。

---

## 4. 产品形态

### 4.1 默认 mode：`native`

- 模型直接看到业务 Tool schemas
- `run_code` 可作为可选 Tool 挂在需要编排的 Skill 上（不必全局强制）

### 4.2 可选 mode：`both`（后期）

- 同时暴露 native + `run_code`
- 不采用 Harness 默认「仅 run_code、其它 Tool 拒绝」的 code-only，除非有明确 Agent preset 需要

### 4.3 `run_code` 工具草图

```ts
parameters: {
  language: 'javascript' | 'python',
  source: string,           // 脚本正文
  // 可选：timeoutMs, memoryMb
}
```

脚本内绑定：

```js
// JS
const rows = await tools.bizdata_entity({ action: 'list', /* ... */ })
return { summary: rows.data.length, sample: rows.data.slice(0, 5) }
```

```python
# Python（后端）
rows = await tools.bizdata_entity(action="list", ...)
return {"count": len(rows["data"])}
```

要点：

- `tools.*` 子调用 = `ctx.tools.execute`，带 parent token，记入轨迹
- **白名单**：仅 `list` / `schema` + 已注册 Tool 名可调用；`tools.filter` / `tools.map` 等不得伪装成合法 Tool（实测3）
- **`tools.schema(name?)`**：读取可见契约的 JSON Schema（与 LLM / 校验同源）；调用前应读必填字段，禁止猜参
- **子调用先 `validateToolArgs` 再 handler**（脚本内非法/空串参数被拦截）
- `tools` **不是数组**：过滤请 `const names = tools.list(); names.filter(...)` 再 `await tools[name](args)`
- 模型历史主要见外层 `run_code` 的 curated 输出；子调用结果进 Surface / 日志
- 禁止：`fetch` 任意 URL、`fs`、`child_process`、动态 `import` 未授权模块（按运行时收紧）

### 4.4 三套工具视图必须同源（实测4 硬约束）

| 通道 | 可见集 |
|------|--------|
| native `openaiTools` | 本回合激活 Skill 授权 Tool ∪ harness |
| `run_code` `tools.list()` | **同一**授权名 ∩ **已注册 client Tool**（有 functionRegistry handler） |
| `run_subagent` | **同一**授权交集；禁止越权调未授权 Tool |

禁止：

- 把调不了的 `http_request`（server_builtin）列进 `run_code` 沙箱名单，再「回退」成误导列表
- 用 `run_subagent` 当「发现隐藏业务 Tool」的后门
- 默认用 `run_code` / `tools.list()` 探路；有专用业务 Tool 必须 native 调用

实现：`resolveRunnableClientToolNames(availableToolNames)` + `assertRunnableClientTool`。

## 5. 安全策略

| 项 | 策略 |
|----|------|
| 信任模型 | **containment，非完美安全边界**；与已登录用户的 Tool 权限同级 |
| 超时 | 默认墙钟超时（如 5–15s）；可配置 |
| 输出 | 体积上限 + spill / truncate |
| 审批 | 危险写 Tool 仍走 `tools/pre-execute` / `ask_user`；脚本不能绕过 |
| 审计 | 记录 language、耗时、子 Tool 列表、成败 |

## 6. 服务接缝 `ctx.codeRuntime`

```ts
interface CodeRuntime {
  run(input: {
    language: 'javascript' | 'python'
    source: string
    bindings: { tools: ToolBridge }
    signal?: AbortSignal
    budget?: { maxWallMs?: number; maxOutputChars?: number }
  }): Promise<{ value: unknown; logs?: string[] }>
}
```

Provider：

- `code-runtime-browser-worker`（前端）
- `code-runtime-node-vm`（后端）
- `code-runtime-python`（后端子进程）

Consumer：`tool-run-code` 插件注册 `run_code`。

---

## 7. 实施顺序（MS3）

1. 后端 JS vm + `run_code` server_builtin（先打通 server Tool 编排）
2. 浏览器 Worker + client Tool bridge
3. Python 后端（schema / SDK 提示与 JS 对齐）
4. Skill 级授权：哪些 Skill 允许 `run_code`
5. 观测：子调用树在调试面板可见

## 8. 验收

- [ ] 无 `run_code` 时行为与现网一致（默认不强制）
- [x] 脚本内非法参数仍被 Schema 拦截
- [x] `tools.schema(name?)` 可读与 LLM 同源的参数契约
- [x] 脚本无法直接调用未授权 Tool（与 native 授权同源；不含调不了的 http_request）
- [x] `run_subagent` 不得越权调用未授权 client Tool（实测4）
- [ ] 超时与输出截断生效
- [ ] 用户可见：外层状态 + 子 Tool Surface（不丢表格等展示）
- [x] 调研类任务：加载 Skill 后直接 native 调 list/get，不出现「run_code 仅注册了 http_request」探路（实测4）

## 9. 明确不做（本期）

- 持久化安装第三方 pip/npm 包供模型随意用
- 把业务 API handler 编写主流程改成「模型写完整 handler 上线」（已有独立 API 能力链路，不与 `run_code` 混为一谈）
- 默认关闭全部 native Tool、只留 `run_code`
