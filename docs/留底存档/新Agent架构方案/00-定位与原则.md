# 00 — 定位与原则

> 合并自：`AI数据底座Agent重设计方案` 第 1–2 章；并升级「业务自动化 Agent」总约束。

---

## 1. 本 Agent 是什么 / 不是什么

### 是

- 挂在 **Web 系统**上的 **业务自动化 Agent**
- 宿主能力：EADAF 数据模型、物化、API 服务、指标、EADAF、采集管道等
- 扩展能力：业务系统（如 FMMS）自带的 Tool + Skill + 展示卡片
- 默认路径：**native tools**（模型直接调用已注册业务 Tool）
- 可选路径：`run_code` 做复杂编排与数据计算（脚本内只能调已注册 Tool）

### 不是

- 不是 Cursor / Claude Code 式的 **编程 Agent**
- 不以 bash、改仓库、Landlock、全盘文件系统为核心
- 不把「给业务系统写功能代码」当交付物（那是研发流程，不是本 Agent）

一句话：

> **能力靠插件组合；知识靠目录按需加载；结果靠标准化 Surface 展示；编排靠可选代码运行时。**

## 2. 从 Harness 看到的表象与底层逻辑

用户看到的成熟 Agent 节奏：

```text
开始：上下文注入（身份 / 约束 / 能力目录摘要）
  └─ 按需：Think → 勘察 Tool → Skill 正文 → 执行 → 更新任务清单
面向用户汇报关键信息（过程态 + 交付物）
  └─ Deep diving：顺着线索下钻，而非一次铺开
最后总结：交付内容 + 下一步建议
```

底层不是「模型聪明」，而是工程约束：

> **把「Agent 会什么」做成常驻目录摘要；把「怎么干」做成正交原子工具/插件；把「干到哪了」做成外部化状态；把「上下文装多少」做成受预算约束的动态窗口；把「用户看见什么」做成与模型文本分离的展示协议。**

EADAF 历史路径上的反向操作：目录=全文 Skill、工具=资源×动词爆炸、状态=一半靠模型记忆、上下文=全量注入+粗暴裁剪、展示=只剩 ThoughtChain 状态行。

## 3. 七条可复用原则

### 原则 0：能力插件化（Capability as Plugin）

- Harness：一切皆 Cordis 插件；换 Provider 即换整类行为。
- EADAF 目标：`@eadaf/ai-base` 内建 Cordis Context（Agent 能力平面），宿主与业务系统用 composition 挂载插件包。
- **不**把整个 React 应用改成 Cordis 应用；只插件化 Tool / Skill / Prompt 段 / Surface / CodeRuntime。

详见 [01-插件内核](./01-插件内核.md)。

### 原则 1：能力目录与能力体分离（Catalog / Body）

| 维度 | 目标态 | EADAF 现状（待改） |
|------|--------|-------------------|
| 常驻注入 | Skill **摘要目录**（slug + 一句话 + 授予 Tool 名） | 全文 `content_markdown` 拼进 system prompt |
| 按需加载 | `skill` 工具拉单个正文 | 无懒加载通道 |
| 效果 | 上下文恒小、注意力聚焦 | 框架协议 + 多 Skill 全文互相稀释 |

### 原则 2：正交工具原语（而非资源×动词爆炸）

- 目标：语义边界清晰、彼此不重叠、模型一眼能选对。
- 现状：156+ Tool 大量同构 CRUD（`bizdata_create_entity` / `update` / `delete` / `list` / `get`…）。
- 合并原则：读操作优先资源级泛化；写操作按业务规则轻重决定合并或保留显式动词。

### 原则 3：上下文经济（Context Economy）

1. 注入最小化（常驻层 / 按需层 / 运行时层）
2. 工具结果按预算截断
3. 历史语义压缩（保留任务清单与目标，而非 `slice(-12)`）

### 原则 4：状态外部化（Externalized State）

- `update_plan` / `task_complete` 方向正确
- 必须收敛为 per-turn / per-session 状态容器，去掉模块级单例污染

### 原则 5：委托与编排（Delegation）

- 批量建模 / 物化 / 建 API 需要 fan-out 原语（subagent / workflow）
- `run_code` 是**同进程内编排**的轻量补充，不是 subagent 的替代品

### 原则 6：汇报协议 + 显式收尾 + 标准化展示

- 过程：Planning next moves / 阶段说明
- 交付：`task_complete.summary` + `next_steps`
- **新增**：Tool 结果必须有用户可见 Surface（table / entity / chart…），禁止「成功了但 UI 只有一行 ThoughtChain」

## 4. 与「工具经常失败」「展示混乱」的直接关系

| 用户感知 | 根因（工程） | 原则 |
|----------|--------------|------|
| 工具调用失败率高 | 无调用前 Schema 校验；DB/前端 schema 双源漂移；错误不可行动 | 2、3、`defineTool` 契约 |
| 必须展示的没展示 | `ChatToolStep` 只有 status；`data` 不进 UI | 6、Surface 协议 |
| 上下文一长就晕 | Skill 全文 + 全量路由一次注入 | 0、1、3 |
| 业务系统难接入 | Tool 全局一次性 `registerFunctionCall`，无插件包边界 | 0、[08](./08-多应用扩展.md) |

## 5. 已做对、必须保留的能力

- `ToolResponse` 信封（`ok` / `verified` / `kind` / `agentHint`）— 强化而非推倒
- 收敛检测（连续相同 Tool / 错误指纹）
- HITL：`ask_user` + `UserChoiceCard`
- 结构化终止雏形：`update_plan` / `task_complete` / `reconcilePlan`
- 语义路由 + `navigate_to_page`（见 [07](./07-语义路由.md)）
- 结果预算 `maxToolResultChars`、同性质批量聚合
