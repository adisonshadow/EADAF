# 08 — 多应用扩展

> 回答：EADAF 数据底座 Agent 与业务系统 Agent 如何共用内核、各自带 Tool/Skill。  
> 合并 Skill 应用绑定结论（[`skill-application-review.md`](../../skill-application-review.md)）。

---

## 1. 问题设定

- **EADAF**：平台宿主，提供数据模型、物化、API、指标、EADAF、采集等 Tool/Skill
- **业务系统**（如 FMMS）：跑在或对接同一套 AI Chat，但拥有**自己的**领域 Tool、Skill、展示卡片
- 二者都不是编程 Agent；都走 `sendMockUserMessage` → Chat → Skill/Tool

不能要求业务系统改 EADAF 核心源码才能加能力。

---

## 2. 分层模型

```text
┌─────────────────────────────────────────────┐
│ 业务前端 / EADAF 前端                         │
│  AIChatProvider(applicationId) + PageScope   │
└─────────────────┬───────────────────────────┘
                  │ boot
┌─────────────────▼───────────────────────────┐
│ @eadaf/ai-base（Cordis Agent 能力平面）       │
│  core: loop / tools / skills / surfaces / …  │
└─────────────────┬───────────────────────────┘
                  │ plugins
     ┌────────────┼────────────┐
     ▼            ▼            ▼
 EADAF host    FMMS pack    Other pack
 tools/skills  tools/skills tools/skills
 surfaces      surfaces     …
```

| 层 | 谁拥有 | 内容 |
|----|--------|------|
| 内核 | `@eadaf/ai-base` | 循环、信封、校验、Surface 词表、harness Tool、可选 codeRuntime |
| 宿主包 | EADAF frontend | bizdata / apiservice / … 插件 |
| 业务包 | 业务仓库 npm 包 | 领域 Tool、Skill Provider、自定义 Surface |
| 治理 DB | 后端 aibase | application 可见 Skill、Skill↔Tool 授权、启停 |

## 3. 业务插件包约定

最小包形状：

```ts
// @acme/ai-pack
export const name = 'acme-ai-pack'
export const inject = ['tools', 'skills', 'surfaces']

export function apply(ctx: Context) {
  ctx.tools.register(defineTool({ name: 'acme_list_orders', /* ... */ }))
  ctx.skills.register({
    slug: 'acme-order-ops',
    name: '订单作业',
    description: '查询与处理订单…',
    // body 可远程或打包 md
  })
  ctx.surfaces.register('acme_order_table', AcmeOrderTable)
}
```

宿主接入：

```ts
<AIChatProvider
  applicationId={ACME_APP_ID}
  plugins={[eadafHostPack, acmePack]}
  …
/>
```

要求：

1. Tool `name` 全局唯一（建议 `acme_` / `fmms_` 前缀）
2. Skill `slug` 唯一；`is_dedicated` + `skill_applications` 绑定该应用
3. 页面用 `fallbackSkillSlugs` 挂业务 Skill
4. UI 触发 AI：`sendMockUserMessage`，禁止直连 completions / toolInvoke

### 3.1 参数契约接入（与 EADAF 共用内核）

业务包任选其一：

1. `registerFunctionCall`（经 `ensureFunctionRegistryContractSource` 自动进契约总线）
2. 或显式：

```ts
import { registerToolContractSource } from '@eadaf/ai-base';

registerToolContractSource({
  id: 'fmms-orders',
  list: () => fmmsTools.map((t) => ({
    name: t.name,
    description: t.description,
    parameters: t.parameters,
    sourceId: 'fmms-orders',
  })),
});
```

DB 只配 Skill↔Tool **授权名**；不要把 parameters 当运行时权威。模型见参、校验拦参、`run_code` 的 `tools.schema` 都读同一解析结果。详见 [03 §6.1](./03-Tool与参数契约.md)。

## 4. DB 治理 vs 代码运行时

| 关注点 | DB | 插件代码 |
|--------|-----|----------|
| 应用能看见哪些 Skill | ✅ | |
| Skill 关联哪些 Tool 名 | ✅（授权） | Tool 必须已注册 |
| parameters / handler / present | 可选镜像 | ✅ 权威 |
| Skill 正文 | 过渡存 DB | 目标 Git / 包内 md |
| 启停、审计 | ✅ | |

启动校验：授权 tool 名 ⊆ `ctx.tools` 已注册；缺注册 → 明确告警。

## 5. 与外部应用接入指南的关系

[`external-app-integration-guide.md`](../../external-app-integration-guide.md) 讲的是 **API Token / 数据 API / 采集**，不是 Agent 插件。

业务系统若只要调 EADAF 数据 API：走外部接入指南。  
业务系统若要 **嵌入同一套 AI Chat 并扩展自动化**：走本文插件包 + application 绑定 Skill。

两者可同时存在：Agent Tool 内部仍调用已发布 API / 客户端服务。

---

## 6. 可见性与安全

- 无 `applicationId`：capabilities 不返回业务专用 Skill（现有行为）
- 业务 Tool handler 必须在**已鉴权**的前端会话中执行；server Tool 走后端鉴权
- `run_code` 不能突破 Tool 授权集
- Public `GET /ai/skills/:slug` 仍依赖前端白名单——中长期可加 application 闸门（审查中已记录）

---

## 7. 示例路线（MS5）

1. 抽出 EADAF host pack（从 `AIChatClientToolsRegistrar` 迁移）
2. 写一份「最小业务包」模板（1 Skill + 2 Tool + 1 Surface）
3. 用独立 `applicationId` 联调：目录可见、正文可加载、表格可展示
4. 文档化到业务团队（可不单开对外长文；以模板仓库为准）

---

## 8. 验收

- [ ] 业务包不改 ai-base 源码即可注册 Tool/Skill/Surface
- [ ] 卸载应用 / dispose Context 后无 handler 泄漏
- [ ] 应用 A 的专用 Skill 不会出现在应用 B 的目录
- [ ] 业务 list Tool 默认打出 table Surface
